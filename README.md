# OpenAppShelf

[GitHub](https://github.com/youtae/OpenAppShelf) · [MIT License](LICENSE)

일반 사용자도 오픈소스 앱을 발견하고 공식 설치 파일을 쉽게 찾는 카탈로그입니다. 앱의 용도, 지원 환경, 공식 다운로드와 설치 안내를 함께 모읍니다.

**[apps.json](apps.json)이 카탈로그 원본입니다.** JSON을 검증해 아래 링크 목록을 생성하고, PostgreSQL에 동기화합니다. 웹사이트는 DB 검색 API를 사용합니다. GitHub에서 목록을 읽거나 JSON으로 기여하는 데는 서버와 DB가 필요하지 않습니다.

[2026-09-07 설치 정보 검수](INSTALL-AUDIT.md): 100개 앱의 공식 릴리스와 설치 파일을 대조하고 누락된 선택지·지원 조건·링크를 수정했습니다. 설치 파일의 실제 실행 검증과는 구분합니다.

## 기여하기

1. `apps.json`의 기존 항목을 참고해 앱을 추가하거나 수정합니다. 고유한 `id`·`repo`, 분류, 쉬운 한국어 설명, 태그, 준비 조건과 첫 사용 순서를 입력합니다.
2. 공식 저장소의 라이선스와 정식 릴리스를 확인합니다. 릴리스 버전·URL과 파일명·다운로드 URL·크기는 공식 응답을 그대로 사용합니다. 소스 압축본과 디버그 파일은 제외합니다.
3. 실제 확인한 OS와 배포 파일만 등록하고 `checked`에 확인일을 적습니다. 이미지가 없으면 `imageKind: "none"`을 사용합니다. 이미지와 라이선스 원문 출처도 함께 기록합니다.
4. 저장소 루트에서 `npm run readme`와 `npm run check`를 실행하고 새 링크를 확인합니다.
5. `apps.json`과 생성된 `README.md`의 변경을 PR로 제출합니다. 자동 생성 구간은 직접 수정하지 않습니다.

JSON 편집이 어렵다면 공개 저장소의 Issue에 **공식 GitHub 저장소 URL, 해결하는 일, 지원 OS, 공식 설치 파일 링크**를 적어 제보해 주세요. 사용하면서 확인한 준비 조건도 도움이 됩니다. 운영자는 제보를 확인한 뒤 아래 `--repo=owner/repository` 명령으로 동일한 검증 과정을 실행합니다. Issue를 자동으로 읽거나 댓글을 작성하지는 않습니다.

README의 앱 이름은 GitHub 저장소로, 다운로드는 확인한 공식 릴리스로 연결됩니다. 웹사이트에서는 OS와 파일 종류를 선택해 개별 설치 파일을 받을 수 있습니다.

## 개발 환경과 실행

Node.js **24.20.0 LTS**와 PostgreSQL 18을 기준으로 합니다. 지원 Node 버전은 `package.json`의 `engines.node`에 지정되어 있습니다. 서버는 Node 기본 HTTP 모듈과 PostgreSQL 드라이버 `pg`를 사용합니다. 이미지 수집에는 Playwright·Chromium, 소개문 작성에는 설치된 Codex CLI의 App Server를 사용합니다.

기능에 따라 필요한 환경은 다음과 같습니다.

| 하려는 일 | 준비할 것 |
| --- | --- |
| GitHub에서 앱 목록 읽기·JSON 다운로드 | 없음 |
| JSON 수정·README 생성·기본 검사 | Node.js 24.20.0 이상 24.x, npm |
| 웹사이트·검색 서버 실행 | 위 환경 + PostgreSQL 18, 본인의 `DATABASE_URL` |
| 홈페이지 이미지 추출·캡처 | Node.js + Playwright Chromium |
| GitHub 후보 수집·AI 소개 작성 | 위 이미지 환경 + Codex CLI, 본인의 ChatGPT 로그인 |

공개 저장소를 내려받은 뒤 저장소 루트에서 실행합니다. `package-lock.json`으로 동일한 라이브러리 버전을 설치합니다.

```sh
git clone https://github.com/youtae/OpenAppShelf.git
cd OpenAppShelf
npm ci
npm run check
```

여기까지는 DB·Codex 로그인·브라우저 설치 없이 실행할 수 있습니다. 기존 앱 이미지도 저장소에 포함되므로 단순 목록 편집이나 웹사이트 실행을 위해 이미지를 다시 수집할 필요가 없습니다.

웹사이트를 실행하려면 PostgreSQL에 이 프로젝트 전용 DB를 준비하고 연결 주소를 환경 변수 `DATABASE_URL` 또는 저장소 루트의 `.env`에 설정합니다. `.env`는 각 사용자가 만드는 개인 설정 파일이며 공유하지 않습니다. 예시의 사용자명·비밀번호·포트는 자신의 환경에 맞게 바꿉니다.

```dotenv
DATABASE_URL=postgresql://username:password@127.0.0.1:5432/open_app_shelf
```

DB 계정에는 초기 동기화 시 테이블과 `pg_trgm` 확장을 생성할 권한이 필요합니다. 운영 환경에서는 동기화 계정과 조회 전용 서버 계정을 나눠 같은 DB에 연결할 수 있습니다.

```sh
npm run readme
npm run sync
npm test
npm start
```

<http://127.0.0.1:4173>에서 열립니다. 서버는 로컬 미리보기 주소에만 바인딩합니다. 공개 배포는 별도 작업입니다.

DB 설치·시작 방법은 각 사용자의 운영체제와 PostgreSQL 설치 방식에 따릅니다. 저장소가 DB 서버나 계정을 자동으로 생성하지는 않습니다. `.env`와 `.local/`은 Git에서 제외하며 다른 사용자의 DB·인증 정보·수집 대기 자료를 복사하지 않습니다.

전체 설치 및 수집 흐름은 macOS에서 검증했으며, Windows·Linux에서는 아직 검증하지 않았습니다.

## 데이터 흐름

```text
apps.json → 검증 → README 앱 목록
               → PostgreSQL app_catalog → Node API → 웹사이트
```

`npm run readme`는 README의 생성 구간만 바꾸고 소개·실행 안내를 보존합니다. DB 연결 없이 실행할 수 있습니다. `npm run check`는 목록이 JSON과 달라지면 실패합니다.

`npm run sync`는 JSON 전체를 검증한 뒤 한 트랜잭션으로 `app_catalog`를 갱신합니다. ID가 같으면 수정하고, 새 ID는 추가하며, JSON에서 제거한 ID는 이 테이블에서도 제거합니다. 동시 동기화는 직렬 처리하고 실패하면 DB 변경 전체를 롤백합니다. 다른 테이블은 건드리지 않습니다. DB에서 JSON으로 역동기화하지 않습니다.

앱 추가·수정 PR을 반영한 뒤 서비스 운영자가 `npm run sync`를 실행해야 웹 검색에 반영됩니다. 후보 수집은 아래 단일 실행 명령이나 독립 Node 워커로 운영할 수 있습니다. 공개 게시·배포는 자동화하지 않습니다.

## 이미지 채우기

```sh
npx playwright install chromium
npm run images
npm run sync
```

기존 공식 이미지는 먼저 로컬에 보관하고, 이미지를 확보할 수 없는 앱에 홈페이지 대표 이미지(`og:image` 또는 `twitter:image`) → 홈페이지 캡처 → 프로젝트 소개 카드 순서로 시각 자료를 채웁니다. 소개 카드는 홈페이지 화면이 아니라는 문구를 포함합니다. 특정 앱의 홈페이지를 다시 캡처하려면 `npm run images -- --id=keepassxc --screenshot`을 실행합니다.

이미지는 `assets/previews/`에 저장하며 경로·유형·출처·확인일을 JSON에 기록합니다. 이미지 파일과 JSON 변경을 함께 PR에 포함하세요. 홈페이지 캡처는 로그인 정보 없이 JavaScript를 끈 브라우저에서 처리하므로 동적 화면은 원래 사이트와 다를 수 있습니다. 내부망 주소·비 HTTPS 주소·과도한 리다이렉트·대용량 응답을 차단합니다. 원본 이미지는 출처 프로젝트의 권리를 따르며 수집 사실이 재배포 허가를 의미하지 않습니다.

## GitHub 후보 자율 수집

운영자가 한 번 명령을 실행하면 후보 검색, 중복 제외, 공식 라이선스·릴리스·설치 파일 확인, Codex의 한국어 소개 작성, 이미지 수집, 후보 JSON 저장까지 진행합니다. 기본 후보 출처는 **GitHub 검색 API**입니다.

Codex CLI에서 `codex login`으로 ChatGPT 로그인을 마친 상태여야 합니다. [Codex App Server](https://developers.openai.com/codex/app-server)의 로컬 stdio 프로토콜을 사용하며 별도 OpenAI API 키는 필요하지 않습니다. 모델에 맞는 최신 CLI를 사용하세요. npm으로 설치·업데이트하고 버전을 확인합니다.

```sh
npm install -g @openai/codex@latest
codex --version
codex login
npx playwright install chromium
npm run check:codex
npm run collect -- --limit=3
```

Codex CLI의 설치 방식은 자유롭고, 터미널에서 `codex` 명령이 실행되면 됩니다. 각 운영자는 **본인의 Codex 사용 권한과 ChatGPT 로그인**을 사용합니다. 현재 수집기는 ChatGPT 로그인 방식만 지원하므로 API 키만 사용하는 계정은 아직 지원하지 않습니다. 웹사이트 방문자와 일반 목록 기여자에게는 Codex 계정이 필요하지 않습니다.

`check:codex`와 소개문을 작성하는 `collect`는 실제 Codex 사용량을 소비합니다. 아래 `collect -- --refresh`는 GitHub만 조회하므로 Codex 로그인·사용량과 Chromium 설치가 필요하지 않습니다. 기본 모델은 Codex 설정을 따릅니다. 다른 설치본을 사용하려면 `.env`의 `CODEX_BIN`에 실행 파일 경로를, 모델을 명시하려면 `CODEX_MODEL`을 지정할 수 있습니다. 선택 설정이며 기본 실행에는 필요하지 않습니다.

```sh
npm run collect -- --query="topic:desktop-app archived:false fork:false stars:>100" --limit=3 --scan=12
npm run collect -- --repo=owner/repository --limit=1
```

검색어를 지정하지 않으면 **실행할 때마다** 사진 편집 → 백업 → 문서·노트 → 음악 → 파일 관리 → Windows → macOS → Linux 설치 파일(AppImage) → 신규 프로젝트 순으로 검색합니다. 일반 검색은 별 20개 초과, 신규 검색은 최근 365일 생성·별 0–100개인 데스크톱 관련 저장소를 대상으로 합니다. 모두 최근 업데이트 순으로 조회하며 보관·포크 저장소를 제외합니다. 별 수는 검색 범위를 나누는 기준이며 품질 점수가 아닙니다. 광범위한 OS 검색에 섞이는 라이브러리는 설치 파일 검사와 Codex 적합성 검토에서 거릅니다.

`limit`은 Codex로 검토할 최대 저장소 수(1–5, 기본 3), `scan`은 한 번에 확인할 검색 결과의 상한(1–20, 기본 12)입니다. 검색 주제별 다음 페이지·위치를 기존 배치 기록의 `search`에 남겨 다음 순환 때 이어서 확인합니다. 페이지 끝에서는 `scan`보다 적게 확인할 수 있으며 검색 끝 또는 1,000개에 도달하면 처음부터 다시 확인합니다. 직접 지정한 `--query`도 검색어별로 이어서 조회하고 자동 순환 순서를 바꾸지 않습니다. `--repo`는 검색을 거치지 않고 지정한 저장소를 검증합니다.

이미 등록했거나 검토 대기 중인 저장소는 제외합니다. 흔히 쓰이는 오픈소스 라이선스와 명확히 식별되는 정식 설치 파일만 후보로 만들고, 다른 라이선스·불명확한 압축 파일·보관된 저장소는 사유를 기록합니다. 데스크톱용 자동 선별에서는 소스·디버그 심볼·CLI·원격 확장 호스트(REH) 파일과 FreeBSD 등 미지원 OS 패키지도 제외합니다. 별도 CLI 앱을 소개하려면 용도와 실행 방법을 수동 검토해 기여하세요. 조건에 맞는 앱이 없으면 후보 없이 종료할 수 있습니다. 결과 순서는 GitHub의 갱신에 따라 이동하므로 모든 저장소를 빠짐없이 탐색한다는 보장은 없습니다. `.local/collections/` 기록을 삭제하면 순환·진행 위치·대기 후보 중복 제외도 초기화됩니다. 같은 작업 폴더에서는 수집 명령을 동시에 실행하지 마세요.

GitHub 요청 제한에 걸리면 중단 사유와 확보한 근거를 저장합니다. 선택적으로 `.env`의 `GITHUB_TOKEN`을 사용하며 토큰은 GitHub API에만 보냅니다.

Codex에는 수집한 공개 저장소 설명·README·파일명만 전달합니다. URL·릴리스·파일 크기는 모델이 작성하지 않고 GitHub API에서 가져옵니다. 저장소 문서는 지시가 아닌 자료로 취급하고, 수집용 Codex에서 셸·앱·플러그인·사용자 메모리 도구를 끕니다. 모델은 설명과 분류를 작성하며 오류가 있을 수 있으므로 게시 전 검토가 필요합니다.

결과는 `.local/collections/<배치명>.json`의 `candidates`, `skipped`, `evidence`에 저장됩니다. 오류가 나도 확보한 근거는 보존합니다. **자동으로 기존 JSON·README·DB에 게시하지 않습니다.** 웹 관리자에서 개별 검토하거나, 워커를 중지한 뒤 아래 CLI 명령으로 배치 전체를 반영합니다.

```sh
npm run collect -- --accept=<배치명>.json
npm run readme
npm run sync
npm test
```

수락 시 기존 JSON을 `.local/`에 백업하고 중복·URL·스키마를 검증합니다. 홈페이지 이미지 추가도 같은 방식으로 원본을 백업합니다. 수집은 서버의 공개 API에 노출하지 않으며 계정·토큰·DB·후보 작업 자료가 있는 `.env`와 `.local/`은 Git에서 제외합니다.

### 관리자 페이지

`npm start`로 서버를 실행한 컴퓨터에서 [후보 검토](http://127.0.0.1:4173/admin)를 엽니다. 기존 DB 설정을 사용하며 추가 패키지나 외부 계정은 필요하지 않습니다. 로그인 전에는 후보 조회·승인 API를 사용할 수 없습니다.

처음 실행하면 설치마다 다른 관리자 키를 자동 생성합니다. 프로젝트 폴더의 **대화형 터미널**에서 확인한 키를 로그인 화면에 입력하세요. 일반 서버 로그에는 키를 출력하지 않습니다.

```sh
npm run admin -- key
```

직접 정한 비밀번호를 쓰려면 다음 명령을 실행하고 비밀번호를 두 번 입력하세요. 입력 내용은 화면에 표시되지 않습니다. 비밀번호는 12~256자이며 원문 대신 salt와 scrypt 해시로 저장합니다. 비밀번호를 잊어도 설치한 컴퓨터에서 같은 명령으로 재설정할 수 있습니다.

```sh
npm run admin -- password
```

다시 자동 키 방식으로 전환하거나 키를 새로 발급하려면 `npm run admin -- generate-key`를 실행하세요. **두 방식 중 하나가 활성화되며**, 전환·재설정하면 이전 키/비밀번호와 기존 로그인 세션은 무효화됩니다. `key`는 현재 자동 키를 확인만 하고 재발급하지 않습니다.

인증 정보는 Git에서 제외되는 `.local/admin-auth.json`에 소유자 전용 권한(0600)으로 저장됩니다. 자동 키는 터미널에서 다시 확인할 수 있도록 이 파일에 보관하므로 공유하지 마세요. 로그인은 최대 12시간 유지되고 로그아웃·서버 재시작·인증 정보 변경 시 종료됩니다. 세션은 서버 메모리에 보관하며 브라우저에는 `HttpOnly`, `SameSite=Strict` 쿠키만 전달합니다. 로그인 시도는 서버 전체에서 분당 5회로 제한합니다. 현재는 HTTP 루프백 전용이므로 외부 HTTPS 배포 지원 시 Secure 쿠키와 프록시 신뢰 설정을 별도로 구현해야 합니다.

- **승인하고 공개**: 선택한 후보만 `apps.json`에 추가하고 README와 검색 DB에 반영합니다. Git 커밋·푸시나 외부 배포는 하지 않습니다.
- **보류 / 거절**: 공개하지 않고 상태를 `.local/reviews.json`에 저장합니다. 해당 탭에서 검토 대기로 되돌릴 수 있습니다. 수집 원본은 보존하며 같은 저장소를 다시 수집하지 않습니다.
- 후보 옆 체크박스로 여러 앱을 고르거나 **현재 목록 전체 선택**으로 한 번에 선택한 뒤, **선택 승인하고 공개 / 선택 보류 / 선택 거절 / 선택 대기로**를 실행합니다. 전체 선택은 현재 상태 탭의 미승인 후보만 대상으로 하며 탭을 바꾸면 선택을 해제합니다. 선택한 후보 중 변경·처리·삭제된 항목이 있으면 쓰기 전에 전체 요청을 취소합니다. 일괄 승인은 JSON·README·DB를 한 번씩 반영합니다.
- 이미지와 출처, 소개, 준비 조건, 시작 방법, 라이선스 원문, 공식 릴리스·설치 파일을 확인할 수 있습니다. 기존 앱의 릴리스 변경 승인은 아직 CLI 보고서를 통한 수동 검토 대상입니다.

웹 검토 중에도 자동 수집 워커를 계속 실행할 수 있습니다. 수집 배치는 완성 후 원자적으로 저장하고, 웹 승인과 CLI 승인은 `.local/catalog-write.lock`으로 동시 쓰기를 막습니다. 승인 전 원본은 `.local/review-backups/`에 보관합니다. 승인 중 DB 오류나 프로세스 종료가 발생하면 `apps.json`을 기준으로 복구하며, 관리자 화면의 **다시 동기화**로 README와 DB 반영을 끝냅니다. `.local/review-publication.json`은 그 미완료 상태를 기록합니다. 수동 JSON 편집·이미지 갱신·CLI 동기화는 웹 승인과 동시에 실행하지 마세요.

관리자 페이지와 API는 루프백 연결·로컬 Host를 검사합니다. 후보 조회·변경에는 로그인 세션이 필요하고, 변경 요청에는 같은 출처와 세션별 CSRF 토큰도 요구합니다. 외부 프록시 전달 헤더를 거부하며 원격 관리자 로그인은 제공하지 않습니다. 공개 호스팅에서 이 제한을 제거하거나 프록시로 우회하지 마세요. 잠금 파일이 남으면 파일의 PID가 종료되었는지 확인한 뒤 잠금 파일만 제거하세요. `npm test`는 임시 인증 파일·임시 DB 테이블로 두 로그인 방식, 세션 무효화, 비인증 접근 차단, 승인, 보류, 거절, 중복, 동시 쓰기, 동기화 실패 복구를 검증하며 실제 인증 정보나 후보를 변경하지 않습니다.

### 주기적 자동 수집

```sh
npm ci
npx playwright install chromium
codex login
npm run check
npm run collect:watch
```

`collect-worker.mjs`는 `collect.mjs`를 주기적으로 실행하는 Node 프로세스입니다. Node·Chromium·Codex CLI와 ChatGPT 로그인이 필요하며, 수집에 DB는 필요하지 않습니다.

처음 시작하면 후보 검색·소개·이미지 수집(`--limit=3 --scan=12`)을 실행한 뒤 등록 앱 12개의 릴리스를 점검합니다. 두 단계가 성공하면 완료 시점에서 3시간 후 반복하고, 실패하면 다음 단계를 중단하고 1시간 후 재시도합니다. 후보가 0개인 경우도 정상 결과일 수 있습니다. 각 단계의 실행 상한은 30분입니다.

다음 실행 시각과 각 단계의 종료 코드는 `.local/collector-worker.json`에 원자적으로 저장합니다. 재시작하면 최근 완료 시각과 실행 결과에 현재 주기를 적용해 다음 시각을 다시 계산하고, 이미 지났으면 한 번 실행합니다. 누락된 날짜만큼 몰아서 실행하지 않습니다. 후보·제외 사유·릴리스 변경은 기존 `.local/collections/`에 남으며 공개 JSON·README·DB에는 자동 반영하지 않습니다.

macOS·Linux에서 터미널을 닫은 뒤에도 실행하려면 저장소 루트에서 다음과 같이 시작합니다.

```sh
mkdir -p .local
nohup npm run collect:watch > .local/collector-worker.log 2>&1 &
```

상태는 `.local/collector-worker.json`, 로그는 `.local/collector-worker.log`에서 확인합니다. 포그라운드 실행은 Ctrl+C로, 백그라운드 실행은 상태 파일의 PID가 해당 워커인지 확인한 뒤 `kill <PID>`로 중지합니다. 정상 종료 시 잠금 파일을 제거합니다. 강제 종료로 `.local/collector-worker.lock`이 남았다면 그 안의 PID가 더 이상 실행 중이 아님을 확인한 뒤 잠금 파일만 제거하고 재시작하세요.

같은 폴더의 워커 중복 실행은 잠금으로 차단합니다. 워커 실행 중에는 수동 `collect`·CLI `--accept`·이미지 갱신을 동시에 실행하지 마세요. 웹 관리자 검토는 워커와 함께 사용할 수 있습니다. macOS·Linux에서는 중지·시간 초과 시 해당 수집 단계의 자식 프로세스 그룹에 종료 신호를 보냅니다. Windows의 전체 수집·종료 동작은 아직 검증하지 않았습니다.

실행할 컴퓨터와 프로세스가 켜져 있어야 합니다. 절전 중에는 작업이 멈추며, 재부팅 후 자동 기동은 포함하지 않습니다. 본인의 운영 환경에서 프로세스 관리자를 사용하는 경우 위 포그라운드 명령을 등록하면 됩니다. Codex 로그인 만료·사용량 제한이나 GitHub 제한이 발생하면 로그를 확인하고 계정 상태를 복구해야 합니다.

오픈소스 검증은 `npm run check`로 일정 계산·재시작·잠금·자식 종료 코드 처리를 검사하고, 실제 검증은 워커가 남긴 상태와 배치 JSON으로 확인합니다. 외부 API·Codex·이미지 수집 성공은 기본 검사 통과만으로 판단하지 않습니다.

### 기존 앱의 릴리스 재확인

```sh
npm run collect -- --refresh --scan=12
npm run collect -- --refresh --repo=localsend/localsend
```

등록된 앱 중 마지막 점검 시도가 오래된 순서로 최대 `scan`개를 조회합니다. 같은 명령을 반복하면 점검한 앱은 뒤로 이동합니다. 실패한 앱도 다음 순환에 다시 시도해 특정 오류가 다른 앱의 점검을 계속 막지 않도록 합니다. 버전뿐 아니라 같은 릴리스의 설치 파일 추가·제거·URL·크기 변경도 비교합니다. 파일 순서와 표시 문구만 달라진 경우에는 변경으로 처리하지 않습니다. 기존 카탈로그에 일부 파일만 등록했다면 처음 점검할 때 그 차이도 표시됩니다.

보고서의 `releaseChecks`에는 `unchanged`, `changed`, `error`와 공식 릴리스 URL 또는 오류 사유를 기록합니다. 변경이 있으면 검토할 `proposed` 항목을 포함합니다. 정식 설치 파일을 찾지 못하면 오류로 남겨 기존 다운로드 정보를 보존합니다. `--accept`는 신규 후보 전용입니다. 릴리스 변경은 준비 조건·OS·파일을 확인한 뒤 `apps.json`에 수동 반영하고 `npm run readme`, `npm run check`를 실행해 PR로 제출하세요. 반영 후 운영자가 `npm run sync`를 실행합니다. 이 점검은 설치 파일을 내려받거나 실행하지 않습니다.

## 검색 API

| 요청 | 응답 |
| --- | --- |
| `GET /api/apps?q=영상&category=video&os=windows&easy=1&page=1&limit=24` | `{ items, total, page, limit }` |
| `GET /api/apps/localsend` | 앱 상세와 공식 파일 목록 |
| `GET /apps.json` | Git에서 관리하는 공개 원본 |

검색은 이름·요약·설명·태그의 대소문자를 구분하지 않는 부분 문자열 검색입니다. 공백으로 나눈 단어를 모두 포함해야 하며 한국어는 NFC로 정규화합니다. `%`와 `_`는 검색 문자 자체로 처리합니다. `pg_trgm` GIN 인덱스를 만들지만 아주 짧은 검색어의 성능은 데이터량에 따라 달라집니다. 벡터·의미 검색과 오타 보정은 아직 없습니다.

`category`는 `all/everyday/photo/video/productivity/developer`, `os`는 `all/macos/windows/linux`, `easy`는 `0/1`입니다. 기본 페이지 크기는 24, 최대 100이며 JSON 순서를 유지합니다. 검색어는 최대 120자입니다. 잘못된 조건은 400, 없는 앱은 404, DB 조회 장애는 503으로 응답합니다. SQL 매개변수를 사용하고 API는 읽기 전용입니다.

## 검증

- `npm run check`: JavaScript 문법, 카탈로그 스키마·중복·공식 다운로드 URL, 검색·설치 파일 선택·HTML 이스케이프, README 일치, 이미지 형식·경로·내부망 차단·설치 파일 분류, 발굴 검색 순환·이어가기·릴리스 변경 감지·재확인 순서, 워커의 일정·잠금·자식 종료 코드 검사. DB와 실제 Codex 요청 없이 실행합니다.
- `npm test`: 위 검사와 실제 PostgreSQL/HTTP 통합 검사. 먼저 `npm run sync`를 실행합니다. 임시 테이블에서 추가·수정·제거·재동기화·실패 롤백을 검사하고 실제 카탈로그는 변경하지 않습니다. JSON/DB 내용 일치, 한국어·영문 검색, 복합 필터, 페이지 나누기, 상세, 잘못된 입력과 비공개 경로 차단도 확인합니다. 테스트 계정에는 임시 테이블 생성 권한이 필요합니다.

별도 린터·TypeScript·테스트 프레임워크는 사용하지 않습니다. 테스트는 Node 기본 모듈로 실행합니다.
